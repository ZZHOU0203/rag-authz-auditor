# 授权后的修复流程

仅在用户授权修改审查范围内的代码时读取。审查请求本身不授予修改权限；沿用本次会话已有的有效授权和项目规则，不增加重复审批。

## 确定修复边界

按 SKILL.md“确认发现的门槛”核对权限契约、原程序可达路径和违反观察，再说明已确认的问题、触发条件、涉及的入口与计划修改的文件。不能为缺少这些依据的候选问题直接增加同步或权限机制；另受委托设计或加固规则时，按“关键语义确认”区分新方案与旧漏洞修复，不能借任务改名绕过待答问题。检查当前工作区的已有改动，保留用户工作；不要为修复顺带改造框架、格式化无关文件或改变业务权限约定。

权限要求不明确且会改变漏洞结论或修复结果时，执行 SKILL.md“关键语义确认”，包括核对回复是否确实解决缺失规则；收到回复不等于完成确认，要求继续审查也不授权自行定规则。未解决的部分不按假设改动，报告剩余问题并继续处理不依赖答案的部分；已有明确权威规则不重复问，原有有效修复授权继续适用。用户只授权某个问题时，其他发现写进报告；不要自行扩大修改范围。

## 找到并修复通用根因

沿实际调用路径查找同一规则的调用方及已有测试，先判断问题位于某个局部检查、共享授权逻辑还是状态更新方式。多个入口因同一规则分叉而出错时，在共同职责处做最小结构修正；证据只支持局部错误时，做局部修复。

保留原有输入校验、错误处理、人工审批和数据保护。不要按测试文档名、行业、租户 ID 或某段提示词写特殊分支，也不要通过屏蔽引用、依赖模型自律或绕过拒绝结果掩盖正文泄露。复用项目现有结构，只有根因需要时才增加依赖或抽象。

## 验证真实行为

先确认相关命令只使用隔离数据和允许的服务。修复编辑与验证执行均按 SKILL.md“执行前后核对文件变化”建立基线、核对最终差异并记录过程产物；不要只用源码差异代替副作用核对。选择能验证根因的最小测试范围，覆盖有权访问、无权拒绝与相关边界，并核对实际输出内容、模型输入或工具结果以及数据副作用；具体观察点由受影响路径决定。

复现原失败，并为确认的问题新增或保留回归测试。共享逻辑变化还要检查受影响入口；撤权问题按项目已确认的撤权生效约定检查状态变化后的请求和在途结果，引用问题同时检查正文与来源读取。按 SKILL.md“用证据验证判断”补齐未受影响的合法访问控制，以及已有持久化机制的同数据关闭重开或相关进程重启验证；如不能执行，明确列为未测，不以当前实例的结果代替。不要只用一个函数返回值代替整条相关路径的证据。

失败时记录可复现输入、实际结果、预期行为和影响，先区分实现、测试设施与环境原因。修复通用根因后重跑原失败及相关回归，不能删除、跳过或弱化既有断言来获得通过。需求确已改变时，需要用户确认后才能更新对应期望，并说明原因。

不要求为纯授权逻辑调用真实模型；实际后端配模拟模型通常能观察资料是否越过权限边界，但必须按真实证据标注测试类型。不能安装依赖、启动服务或确认隔离时，完成已授权且可静态审查的代码修改，提供待运行命令和预期行为，将验证状态写为未验证。不要编造命令输出，也不要为获取通过结果连接生产系统。

## 交付并停止

报告根因、修改范围、行为变化、测试命令与实际结果、未解决问题、未验证范围和真实副作用。必要测试仍失败时明确写出修复未通过验证；静态检查通过只证明相应静态条件。

在已授权范围完成且相关验证通过后停止。若环境或权限阻塞后续步骤，交付已有结果与具体阻塞条件；不要无限重试、自动发布或把本次修复描述为整个应用的安全认证。
